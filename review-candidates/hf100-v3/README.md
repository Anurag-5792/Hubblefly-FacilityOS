# HF100 V3 — AWS-free retained Roles-only installer

This successor is a direct child of Chat13's host probe and preserves accepted V2 and frozen SQL byte for byte. No resource provisioning, AWS account, new database, new reviewer, runtime role activation or stock access. The signed original HF11 combined standing order is normalized using the accepted original template digest, with only its designated final fields bound to this successor; machine contract schema HF100_MACHINE_CONTRACT_V3 is the new versioned binding. Do not sign an unresolved contract.

## Existing qualified host

Use an already covered existing Vercel Sandbox or corporate Linux/WSL. The host must provide nonroot execution, root-owned nonwritable checkout/toolchain, exact PG18 client/server binaries, Python, GPG and unshare --user --map-current-user --net. No automatic Sandbox creation/resume or cost-bearing activity. Chat13 verifies actual host identity/cost and direct TLS with the preserved tools/hf100-host-probe/hf100_host_probe.py. The V3 signed host record binds kind, host_id, uid, source_root, machine_id_path/hash, Python hash, root-owned dependency manifest path/hash and pg_bin. Host_id is an owner-bound identity plus local measurement, not cloud-provider attestation. The manifest must cover the pinned binaries and actual interpreter/libraries/dependency files. Existing managed private passfile only; exact CA hash and verify-full/channel binding required. The runner rechecks live wire and provider database id/OID/version. No runtime serverless/Vercel deployment execution. No local root restore.

## Authority and custody

One corporate OpenPGP owner signature on exact original combined order, with final successor commit/tree, runner digest and canonical machine-contract digest. Review only new delta. Contract fields in tools/hf100_control.py (combined); use original HF11 canonical bytes, canonical compact sorted JSON contract ending LF. Bind exact accepted GitHub CI and security/key-policy references, frozen target-derived initial baseline digest (computed by --measure-baseline on qualified host), host/tool hashes, two existing private Drive folders, identities and ACL digests. Control folder must contain exactly three files: ACTIVE status JSON, enrolled owner keyring, recovery public keyring. Each signed pin includes actual file ID, current monotonic Drive version, content hash and ACL hash; status exact schema HF100_ACTIVE_V3 with order nonce, owner fingerprint, expiry and state ACTIVE. It does not create authority on its own. Current signed owner keyring and signature verified before target mutation, and current control fetched again before DDL. Changing/revoking/adding STOP, deletion, missing data, version drift or expiry stops the run. A prior version restored through ordinary Drive update has a changed version. Do not reactivate. No human second signer or repeated routine release signature.

Use separately scoped existing Drive tokens HFT_HF100_DRIVE_CONTROL_TOKEN (read control), HFT_HF100_DRIVE_CUSTODY_TOKEN (write/read evidence). Pin about.user.permissionId, folder and file ACL normalized hashes. Only explicit user permissions; no domain/anyone/group sharing. ACL digest is SHA256 of compact canonical sorted JSON list of id/type/role. Full paginated folder and permission census, exact IDs, versions, parents, sizes and content readback required. Existing recovery private key home HFT_HF094_RECOVERY_GNUPGHOME; no keys created by runner. A private 32-byte machine receipt HMAC key is hash-bound in signed contract and must be separately held by the owner for receipt verification. HMAC authenticity is not nonrepudiation. All files are restricted. No live credentials on CI.

## Transaction and recovery

The first authorized mutation is a separate serializable claim on the existing retained DB, protected by a fixed advisory lock, fixed action/target, independent commit and separate NOLOGIN registry owner. An external Drive claim intent is written and read back first. The exact initial empty catalog must match signed baseline; registry bootstrap adds only public.hf100_install_receipt, its index/types and public.hf100_append_receipt, and the restricted owner (public schema stays unchanged). Temporary owner SET/CREATE removed; installer receives only SELECT for actual pg_dump and EXECUTE of append function, no explicit ordinary table mutation grant. The signed baseline now includes the complete original role identity/flag and membership census, including effective and SET ROLE read/write/maintain rights. Only the exact named existing provider administrators and predefined data/maintenance roles may have those inherited capabilities; ordinary principals are denied. Eligibility and signed drift checks run before the external witness; the full baseline is checked again in the serializable claim transaction and explicit registry shape/effective privileges are checked before commit. Re-measure the baseline using the corrected exact source before signing. Registry table and function definitions/ACLs and exact receipt chain are checked on each read and in the frozen install transaction. No public or role-runtime access. One claim ever per target/action, regardless of order nonce. Separate commits persist through install rollback. The installer obtains target-derived custom pg_dump after claim, encrypts with pinned recovery key, creates exact private Drive object, reads it back, decrypts actual original, and restores in an isolated native PG18.7 cluster with no TCP listener, using a new network namespace and private Unix socket. It compares actual restored catalog and registry rows/definitions; no caller PASS. Recheck backup object and authenticated capture before DDL. Frozen V1 single serializable SQL and catalog postflight are reused unchanged inside a fresh baseline and registry fence. A new connection independently reads postflight; terminal receipt linked to prior hash in DB and Drive. Any failure/ambiguous commit/missing receipt stops, no automatic retry. A killed process can leave CLAIM or PREPARED without terminal: permanently consumed pending reconciliation. No target restore/cleanup/retry command is provided.

## Residual risk — NOT immutable storage

The registry is permission-restricted, not protected from database owner with CREATEROLE/admin escalation, provider superuser or restoration of an earlier database. Drive versions/ACLs/readback plus a separate external witness detect ordinary changes, but an administrator can delete, rename, suppress or roll back evidence; coordinated loss/rollback of both witnesses or a compromised host/signing key can defeat detection. There is no atomic transaction across Drive and PostgreSQL and no WORM claim. STOP is checked at the last pre-DDL boundary; remote changes after submission cannot cancel the already-running DB transaction. Never restore/recreate control objects, remove claim or reissue authority to bypass an uncertain result. Reconcile catalog and both independently held evidence sets under owner authority. Chat10/11 must accept this bounded nonproduction residual risk before execution. No claim of equivalence to compliance-mode object lock.

## Execution

Offline: python3 -IB tools/hft_roles_only_install_100.py --inspect

Before signing, Chat13 may run --measure-baseline with --owner-order pointing to the unsigned final-shaped candidate, --machine-contract, --passfile and --ca only. The candidate must have a nonzero provisional baseline digest and otherwise exact source/host pins. This is read-only measurement, not admission. Replace the provisional digest with the measured value, recompute the machine contract hash and bind it to the original final fields before signing once.

On the separately qualified existing host, with exact final order/signature, machine contract, private passfile, CA and receipt key:
```sh
python3 -IB tools/hft_roles_only_install_100.py --qualify --owner-order /restricted/order.json --owner-signature /restricted/order.sig --machine-contract /restricted/contract.json --passfile /restricted/pgpass --ca /restricted/ca.pem --receipt-key /restricted/receipt.key
```
Set HFT_ENVIRONMENT=retained-stores-nonproduction, HFT_LIVE_POSTING_ENABLED=false; provision existing GitHub/Neon read tokens under HFT_HF094_GITHUB_READ_TOKEN/HFT_HF094_NEON_READ_TOKEN and the Drive/recovery inputs privately. Qualify is read-only and makes no claim, dump or restore. After final admission, replace --qualify with --apply exactly once. Do not execute individual SQL, manufacture session markers or use synthetic CI credentials. Receipt outcomes and separate independent catalog readback are mandatory. Runtime login remains disabled. Actual target admission, real Drive and host qualification, and live activation are separate.

CI executes frozen-byte checks, actual disposable PG18.7 registry/installation/rollback/readback, actual target-shaped encrypted dump and native recovery worker in an isolated no-network CI container, synthetic Drive/authority transport and failure injection.
