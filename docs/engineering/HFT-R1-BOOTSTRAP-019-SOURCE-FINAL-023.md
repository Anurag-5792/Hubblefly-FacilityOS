## 4. Restricted-role creation and credentials

BOOTSTRAP-019 now creates only the roles needed for canonical staging:

- `hft_staging_migration_owner` — LOGIN, restricted migration/object owner;
- `hft_r1_app_runtime` — NOLOGIN capability group;
- `hft_staging_app_runtime` — LOGIN, member of runtime group only;

- `hft_staging_audit_verify` — LOGIN, member of audit group only.

No P2/P3/posting-owner/governance roles are created in this bootstrap.

Neon documentation distinguishes role **creation** through Console/CLI/API (which automatically grants `neon_superuser`) from SQL-created restricted roles. Neon also supports password reset for an existing role, but the API reset returns a generated password. This package therefore uses the lower-exposure attended SQL procedure:

1. create all restricted roles through the reviewed SQL bootstrap **without passwords**;
2. connect as `neondb_owner` through attended `psql`;
3. execute, one at a time:
   - `\password hft_staging_migration_owner`
   - `\password hft_staging_app_runtime`
   - `\password hft_staging_audit_verify`
4. the operator pastes password-manager-generated secrets only at masked prompts;
5. no password appears in argv, SQL source, Git, transcript, file or chat;
6. subsequent runner invocations receive the selected role secret through approved process-secret injection and never log it;
7. before migration, catalog checks must show no restricted role is a member of `neon_superuser` and no restricted role has SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS.
